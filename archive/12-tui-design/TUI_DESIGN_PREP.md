# TUI Design Preparation: Uveddi Application Overview

This document summarizes key aspects of the Uveddi application's current structure and functionality, intended to inform the design and implementation of a new Terminal User Interface (TUI).

## 1. Application Core Functionalities & CLI Commands

The application is primarily driven by command-line interface (CLI) commands, parsed using the `clap` crate.

### 1.1. `analyze` Command

Performs comprehensive code analysis.

**Arguments:**

*   `--path <PATH>`: Path to the project or directory to analyze (file or directory).
*   `--output-format <FORMAT>`: Output format for the analysis report.
    *   Supported: `text`, `json`, `markdown` (default: `markdown`).
*   `--output <FILE_PATH>`: Optional output file path. If not specified, report goes to stdout.
*   `--enable-ai`: Enable AI-powered analysis and explanations.
*   `--ollama-api-url <URL>`: Ollama API URL (can be set via `OLLAMA_API_URL` env var).
*   `--ollama-model <MODEL_NAME>`: Ollama model name (can be set via `OLLAMA_MODEL` env var).
*   `--dead-code-confidence <THRESHOLD>`: Confidence threshold for dead code detection (0.0 to 1.0).
*   `--dead-code-library-mode`: Enable library mode for dead code detection.
*   `--dead-code-ignore-patterns <PATTERNS>`: Comma-separated list of patterns to ignore.
*   `--dead-code-keep-alive <SYMBOLS>`: Comma-separated list of symbols to always keep alive.
*   `--large-classes-max-loc <LINES>`: Max logical lines of code threshold for large classes.
*   `--large-classes-max-methods <COUNT>`: Max number of methods threshold for large classes.
*   `--large-classes-max-fields <COUNT>`: Max number of fields threshold for large classes.
*   `--large-classes-max-complexity <COMPLEXITY>`: Max cyclomatic complexity threshold for large classes.
*   `--large-classes-max-lcom <SCORE>`: Max LCOM score threshold (0.0 to 1.0).
*   `--large-classes-ignore-patterns <PATTERNS>`: Comma-separated list of patterns to ignore.
*   `--large-classes-min-severity <SCORE>`: Minimum severity score for large classes reporting (0-100, default: 25).

**Output:**

*   Returns an `AnalysisReport` containing `content` (the formatted report string) and `metadata` (files analyzed, issues found, AI enhanced status).
*   Printed to stdout or written to the specified output file.

### 1.2. `config` Command

Manages application configuration settings.

**Subcommands:**

*   `show`: Displays the current configuration (from file or environment variables).
    *   `--file <PATH>`: Optional path to a specific config file.
*   `set <KEY> <VALUE>`: Sets a configuration value.
    *   `KEY`: e.g., `ollama_model`.
    *   `VALUE`: The value to set.
    *   `--file <PATH>`: Path to the config file (default: `uveddi.toml`).
*   `validate`: Validates the configuration file.
    *   `--file <PATH>`: Optional path to a specific config file.

### 1.3. `plugin` Command (Requires `wasm-plugins` feature)

Manages WASM plugins for extending analysis capabilities.

**Subcommands:**

*   `list`: Lists installed plugins and displays registry statistics.
*   `install <BINARY_PATH> <MANIFEST_PATH>`: Installs a plugin from its WASM binary and manifest.
*   `uninstall <PLUGIN_NAME_OR_ID>`: Uninstalls a plugin.
*   `info <PLUGIN_NAME_OR_ID>`: Shows detailed information about a specific plugin.
*   `stats`: Displays execution statistics for all plugins (invocations, execution time, memory usage, errors).
*   `monitor`: Monitors real-time resource usage of plugins.
*   `verify <BINARY_PATH> <MANIFEST_PATH>`: Verifies a plugin's integrity and security policy without installing it.

## 2. Output & Reporting

*   **Report Formats:** `text`, `json`, `markdown`.
*   **Report Structure:** Generated by `src/report/mod.rs::ReportGenerator`.
    *   Includes: Executive Summary, Issues by Severity, Detailed Analysis, Architecture Diagrams.
    *   Markdown reports can embed Mermaid diagrams.
    *   JSON reports follow a structured schema.
*   **Output Destination:** Can be stdout or a specified file.

## 3. Configuration Management

*   Configuration can be loaded from `uveddi.toml` files or environment variables.
*   Supports setting specific keys like `ollama_model`.

## 4. Error Handling

*   The application uses `color-eyre` for enhanced error reporting, providing:
    *   Colorized error messages.
    *   Stack traces for debugging.
    *   Contextual error information.
    *   Suggestions for common issues.
*   A TUI should leverage this for clear error displays.

## 5. Background Services

*   `src/main.rs` indicates the presence of a `HealthMonitor` and a `server` module, suggesting a background service. The TUI might need to interact with this service for status updates or real-time data.

## 6. Relevant Dependencies & Libraries

*   `clap`: Already used for CLI parsing; its structure directly informs TUI input design.
*   `tokio`: Asynchronous runtime; essential for non-blocking TUI operations and interacting with async application logic.
*   `color-eyre`: For robust error reporting, which should be integrated into the TUI's error display.
*   `tera`: Template engine used for generating diagrams within reports; potentially useful for rendering complex TUI layouts or dynamic content.
*   `serde`, `serde_json`, `toml`: Used for data serialization/deserialization and configuration file handling.

## 7. TUI Design Considerations

Based on the above, a TUI design should consider:

*   **Main Navigation:** A clear main menu or dashboard to access `Analyze`, `Config`, and `Plugin` functionalities.
*   **Input Forms:** Interactive forms for `analyze` command arguments, allowing users to input paths, select formats, toggle features, and set numeric/list parameters.
*   **Output Display:** A dedicated area for displaying analysis reports. This might require a markdown renderer or a structured view for JSON output.
*   **Configuration Editor:** An interactive screen to view and modify configuration settings.
*   **Plugin Management Interface:** Screens to list, install, uninstall, and view details/stats for plugins.
*   **Asynchronous Operations:** The TUI must handle long-running operations (like analysis) asynchronously, providing progress indicators and preventing UI freezes.
*   **Error Reporting:** A prominent and user-friendly way to display `color-eyre` enhanced error messages.
*   **Real-time Feedback:** Potentially integrate with the background `HealthMonitor` or other services for real-time status updates.
*   **Theming/Styling:** Consider a TUI library that allows for customizable themes to match a modern aesthetic.
